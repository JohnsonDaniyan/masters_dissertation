1. Introduction
This review establishes the academic and technical foundation for the proposed project: an automated adversarial testing tool for assessing FAPI 2.0 Security Profile conformance in financial API implementations. The central question this literature addresses is twofold. First, what does FAPI 2.0 actually require of a conforming implementation, and on what evidence do we know these requirements are sufficient to resist attack? Second, what existing tools and testing methodologies — both industry and academic — already exist for financial API security testing, and where, specifically, do they fall short of the adversarial, specification-aware testing this project proposes?
The review is organised thematically rather than chronologically. It begins with the formal-methods foundation FAPI 2.0 is built on (OAuth 2.0's own formal analysis), moves through FAPI 2.0's constituent mechanisms and the formal security analysis that validates them, and then turns to the practical testing landscape: general-purpose API scanners, the OpenID Foundation's own conformance suite, and the most recent (2025–2026) academic literature on automated API security testing. It closes with a critical synthesis identifying the specific gap this project addresses, and a note on why this gap is a live one rather than a historical artefact.
2. The Formal Methods Foundation: OAuth 2.0
FAPI 2.0 is not an independent protocol; it is a constrained profile of OAuth 2.0 and OpenID Connect. Its security claims therefore rest, in part, on how rigorously the underlying OAuth 2.0 model has itself been examined. Fett, Küsters and Schmitz (2016) provide the methodological basis here: using a Dolev-Yao-style formal model of the web infrastructure (the Web Infrastructure Model, WIM), they modelled all four OAuth 2.0 grant types and formally defined authorisation, authentication, and session integrity properties. Critically, this work did not merely audit an existing implementation — it identified previously unknown vulnerabilities in a standard that had already seen years of production deployment. This is a significant finding in itself: it demonstrates that informal, implementation-led security review had already missed exploitable flaws in the world's most widely deployed authorisation protocol, and it establishes a methodological precedent this project's own adversarial approach depends on — that security properties assumed to hold by convention are not the same as properties formally demonstrated to hold under a defined attacker model. It is this same WIM methodology that Hosseyni, Küsters and Würtele (2025) later extend to analyse FAPI 2.0 directly (Section 4).
3. FAPI 2.0's Constituent Mechanisms
Where Fett et al. (2016) analyse OAuth 2.0 as a whole, FAPI 2.0 is better understood as a curated assembly of individually standardised extensions, each closing a specific gap left open by plain OAuth 2.0. These mechanisms are not redundant, and comparing them directly is instructive.
Lodderstedt, Campbell, Sakimura, Tonge and Skokan (2021) specify Pushed Authorization Requests (PAR), which move authorisation parameters out of the browser-facing front channel into a direct back-channel call to the authorisation server, protecting against parameter tampering possible whenever authorisation data travels through a redirect URL. Sakimura, Bradley and Jones (2021) specify a related but distinct mechanism, JWT-Secured Authorization Requests (JAR), allowing the request itself to be signed. The distinction matters: PAR protects the transport channel, while JAR protects the integrity and authenticity of the request's content, and FAPI 2.0 can use either or both — treating them as interchangeable, as some non-technical implementation guidance does, understates FAPI 2.0's actual threat coverage.
A separate category addresses the authorisation response. Meyer zu Selhausen and Fett (2022) specify Authorization Server Issuer Identification, requiring the authorisation server to embed, and the client to verify, an issuer identifier in the authorisation response — a direct, targeted countermeasure against mix-up attacks, where a client is deceived into believing it completed a flow with one authorisation server when it actually completed it with another.
A third category addresses the token itself. Fett, Campbell, Bradley, Lodderstedt, Jones and Waite (2023) specify DPoP, which sender-constrains access tokens at the application layer via a signed proof included with every request. Bertocci (2021) separately specifies the structure of the access token as a signed JWT, which is what allows a resource server to validate a token's authenticity and its embedded sender-constraining confirmation claim without a round trip to the authorisation server. These specifications are complementary: DPoP defines how a token is bound to a client's key; Bertocci's profile defines the container that carries the evidence of that binding. FAPI 2.0 also permits mutual TLS as an alternative to DPoP for the same purpose — a comparison the formal analysis in Section 4 shows is not a like-for-like substitution.
Finally, Jones, Bradley and Machulak (2015) specify Dynamic Client Registration Management, governing how a client's registered keys and metadata can be updated post-registration. This is easy to treat as a peripheral, administrative concern, but Section 4 shows several of the more serious attacks against FAPI 2.0 hinge specifically on how client key material is registered and rotated over time.
4. Formal Security Analysis of FAPI 2.0: Evidence, Not Assumption
The specifications above describe what FAPI 2.0 requires; they do not, by themselves, prove that following them is sufficient. That evidence comes from Hosseyni, Küsters and Würtele (2025), who extended the WIM methodology to model FAPI 2.0's Security Profile, Message Signing, FAPI-CIBA, and both dynamic client registration and management protocols running in parallel — conducted concurrently with the OpenID Foundation's own standardisation process rather than retrospectively.
The critical value of this work lies in what it found, and in how those findings were treated differently depending on whether they could be fixed. Several attacks were identified and subsequently closed through specification changes: attacker token injection and client impersonation attacks (both stemming from clients that can be misconfigured to use an attacker-controlled token endpoint), and DPoP proof replay, where an attacker who observes a resource request in plaintext can replay its DPoP proof, since neither FAPI 2.0 nor DPoP itself originally mandated one-time-use proofs. Notably, this replay attack does not apply to mTLS-based sender constraining — direct evidence that DPoP and mTLS are not security-equivalent alternatives.
Other attacks were not fixed but formally documented as accepted residual risk. The Browser Swapping attack and the Authorization Request Leak attack were both concluded by the FAPI Working Group to be unpreventable using currently deployed methods, given the attacker capabilities the specification assumes. This is arguably the most consequential finding in this literature for the current project: “FAPI 2.0 conformance” is not synonymous with “immune to attack.” A conformance testing methodology needs the ability to distinguish a genuine implementation defect from a documented, accepted limitation of the standard itself — a distinction a purely declarative conformance test, of the kind discussed in Section 5.2, is not designed to surface.
A further limitation is methodological: the analysis is a symbolic, pen-and-paper proof, not a mechanised or executable one. Hosseyni et al. (2025) explicitly note that mechanising their model is left as future work; their proofs — over forty lemmas and fifty pages of technical report — cannot, as they stand, be run against a live implementation. A formally proven attack is not the same artefact as a runnable test case that can be pointed at an arbitrary black-box authorisation server — this is the precise gap Section 7 returns to.
5. The Practical Testing Landscape
5.1 General-purpose scanners and vulnerable-by-design labs
The dominant tools in general API security testing — OWASP ZAP and Burp Suite — are not designed with FAPI-specific semantics in mind. Practitioner evaluations testing these tools against OWASP's own intentionally vulnerable API, crAPI (OWASP Foundation, n.d.-a), illustrate the point directly: generic web scanners often produce poor or false-positive-heavy results against APIs compared to web applications, because APIs expose business logic and authentication flows that generic crawlers are not built to reason about. More targeted tooling exists at the generic OWASP Top 10 level: the OWASP API Security Testing Framework, ASTF (OWASP Foundation, n.d.-b), automatically detects vulnerabilities based on the OWASP API Security Top 10 (2023), discovering endpoints and running test cases covering the full Top 10 plus GraphQL and gRPC, and has been validated against crAPI directly. However, both ASTF and crAPI are scoped to the generic OWASP API Top 10 (OWASP Foundation, 2023) — neither engages with FAPI-specific requirements such as PAR enforcement, sender-constrained token validation, or restricted client authentication methods. This is the precise capability gap this project's mock Open Banking lab and adversarial test modules are designed to fill.
5.2 FAPI/OpenID conformance suite mechanics: cooperative, not adversarial
The OpenID Foundation itself operates the authoritative conformance mechanism for FAPI, via its certification suite (OpenID Foundation, n.d.). For authorisation-server tests, the conformance suite acts as the OpenID Provider and the implementation under test acts as the relying party, with self-certification results published once a vendor passes. The suite does include some adversarial elements: its documentation for FAPI 2/FAPI 1 Advanced-Final OP testing requires two client registrations with different keys and certificates specifically because the suite tests mixup attacks, such as using a valid access token from one client with the TLS client certificate of another (OpenID Foundation, n.d.) — showing the OpenID Foundation itself recognises adversarial-style probing as valuable within conformance testing.
However, the suite remains fundamentally a cooperative certification tool rather than an independent, attacker-oriented testing instrument. Documentation for one regional profile notes that the suite is not a fully featured OP/bank and has its own limitations, expecting certain events to take place in a predefined order and returning errors even for technically acceptable but unexpected situations. This is consistent with its purpose — certification — rather than independent, black-box assessment of a live or third-party implementation the tester does not control or configure. No publicly documented tool currently reframes FAPI 2.0 conformance checking as a black-box adversarial exercise runnable against an arbitrary implementation without cooperative setup — the specific niche this project occupies.
5.3 Contemporary automated API security testing research (2025–2026)
The most recent academic literature on automated REST API testing confirms this gap persists even in the newest available work. Rooijakkers, Nijsten, Daniele, Weitenberg, Groenewegen and Melissen (2025) present WuppieFuzz, extending coverage-guided fuzzing to stateful REST API testing. Sahin, Zhang, Poth, Rrjolli, Faes, Teng, Xue, Ma and Arcuri (2026) use an OpenAPI-specification “overlay” to improve fuzzing precision, while a related paper by Sahin, Zhang and Arcuri (2026) folds access-policy-violation and injection-attack detection directly into a fuzzing pipeline — one of the few papers in this set to combine authorisation-logic checking with fuzzing rather than treating them separately. Zhang, Shen, Arcuri and Yue (2026) examine flakiness in REST API fuzzing, directly relevant to this project's own requirement to report and analyse a false-positive rate, since a flaky test harness would undermine confidence in any conformance evaluation figures. Dharmaadi, Athanasopoulos and Turkmen (2025) provide a broader survey of fuzzing frameworks for server-side web applications, while Susilo (2025) evaluates REST API fuzzing tools from a human-centred, industry-adoption perspective — a useful corrective to the largely benchmark-driven literature, and consistent with earlier industry-deployment findings (e.g. EvoMaster's use at Volkswagen) that academic fuzzing prototypes do not always transfer cleanly into practitioner workflows.
A second cluster targets specific vulnerability classes with more targeted methods than general fuzzing. Santos Filho, Rodríguez and Feitosa (2025) detect Broken Object-Level Authorization by transforming OpenAPI specifications into coloured Petri nets — a formal modelling technique distinct from both fuzzing and the WIM approach in Section 4, suggesting BOLA detection is converging toward specification-driven formal modelling. Xia, Sun, Zheng, Tan and Su (2025) target excessive data exposure using dynamic code instrumentation (Mockingbird), analysing runtime behaviour rather than treating the API as a pure black box — a methodological tradeoff worth noting, since instrumentation-based approaches can be more precise but require code-level access this project's black-box, external-tester threat model does not assume. Xu, Zeng, Tang, Xiao and Chen (2026) present VOAPI2, a general vulnerability-oriented testing framework, while Kim and Nam (2025) address microservice architectures specifically, proposing adaptive detection of suspicious API interaction flows across service boundaries — relevant background given real Open Banking deployments are frequently built as microservices, though not a dimension this project's lab environment is scoped to test. Haryani, Nurgaida Yutia and Ilmi (2025) describe Robot Framework-based automated SQL injection testing — a narrower, single-vulnerability-class tool that usefully contrasts with the breadth a full adversarial FAPI 2.0 suite requires. Agarwal and Ranjan (2026) address zero-trust API pipeline architecture rather than testing directly, evidencing a broader industry “shift-left” trend that reinforces this project's practical relevance. Ribeiro, Mamede and Ferreira (2026) combine model checking with executable contracts for systematic API testing — model checking having some conceptual kinship with the WIM approach in Section 4, though applied here to general correctness rather than security specifically.
Critically, not one of these fourteen 2025–2026 papers targets OAuth 2.0/OIDC authorisation-and-authentication-flow conformance, let alone FAPI 2.0 specifically. Every vulnerability class covered — BOLA, excessive data exposure, SQL injection, general fuzzing-discoverable bugs — sits within the generic OWASP API Top 10 category identified as a gap in Section 5.1. Even the most recent, most sophisticated automated API testing research available at the time of writing has not been extended to the specific mechanisms (PAR, PKCE, sender-constrained tokens, issuer verification) that define FAPI 2.0 conformance.
6. Industry Context: Why This Matters Now
The practical stakes of this gap are corroborated by industry data. Akamai's 2025 API Security Report found that 88.7% of financial services firms experienced an API-related security incident in the past year, the highest rate of any sector, with average incident costs exceeding $830,000 in the US once downtime, legal costs, and regulatory penalties are included (Openbankingexpo.com, 2025). Separately, Salt Security's reporting identifies broken object-level authorisation as present in roughly 40% of all API attacks, consistent with its position atop the OWASP API Security Top 10 since 2019 (Salt Security, 2026). This threat landscape, combined with FAPI 2.0 only reaching Final Specification status in February 2025 (OpenID Foundation, 2025), establishes both the real-world stakes and the timeliness of testing tooling built specifically around it: adoption is accelerating (already mandatory in Colombia, underway in the UK, Australia, and Brazil) faster than independent testing tooling has caught up.
7. Critical Synthesis and Positioning of This Project
Read together, this literature divides into three distinct categories, each addressing part of the problem space this project targets, but none covering all of it.
First, the normative/specification layer (Bertocci, 2021; Fett et al., 2023; Jones et al., 2015; Lodderstedt et al., 2021; Meyer zu Selhausen & Fett, 2022; Sakimura et al., 2021) defines what a conforming implementation must do, but offers no independent evidence that doing so is sufficient. Second, the formal-analysis layer (Fett et al., 2016; Hosseyni et al., 2025) provides that evidence as a symbolic proof, identifying concrete attacks and — critically — distinguishing fixed vulnerabilities from accepted residual risks, but stops short of an executable testing artefact. Third, the practical-tooling layer — general scanners and vulnerable labs (crAPI, ASTF), the OpenID Foundation's cooperative conformance suite, and the 2025–2026 academic fuzzing/testing literature — provides mature, transferable black-box testing methodology, but is either scoped to the generic OWASP API Top 10 (blind to FAPI-specific requirements) or, in the case of the conformance suite, designed for cooperative self-certification rather than independent adversarial assessment.
This three-way split, rather than any disagreement between the sources, is the main tension this literature surfaces: not whether FAPI 2.0's mechanisms are well-designed (the formal analysis broadly vindicates them once fixes were incorporated), but whether any current combination of specification, proof, and tooling actually allows an independent tester to verify FAPI 2.0 conformance adversarially, against a real, uncooperative, black-box implementation. On the evidence reviewed here, it does not: no publicly available tool sits at the intersection of all three layers — specification-aware of FAPI 2.0's specific requirements, adversarial in methodology, and usable against a black-box implementation without cooperative setup.
8. Conclusion
This review has established that FAPI 2.0's individual mechanisms are well-specified (Section 3) and formally validated, including explicit treatment of which risks remain despite conformance (Section 4). It has also shown that the practical testing landscape — from general-purpose scanners through to the most recent 2025–2026 academic fuzzing literature — has not yet been extended to test these specific mechanisms adversarially and independently (Sections 5–6). The project proposed here addresses this gap directly: taking attack patterns formally identified and proved by Hosseyni et al. (2025) — DPoP proof replay, issuer mix-up, token endpoint misconfiguration — and operationalising them as automated, black-box adversarial test cases runnable against a live FAPI 2.0 implementation, using testing methodology drawn from the fuzzing and specification-driven tooling literature reviewed in Section 5.3. The discussion proceeds, in the following chapters, to the design of the mock Open Banking lab environment and the five-module scanner architecture that implements this approach.
